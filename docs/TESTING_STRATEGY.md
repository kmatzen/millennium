# Testing and release strategy

The default decision is **reject the image**. A release is eligible for a
single, planned hardware acceptance session only after all automated gates
below pass for the same full source commit and the exact image that will be
written. Passing QEMU is never recorded as passing physical hardware.

## Coverage model

`acceptance/inventory.json` is generated from every shipped executable,
systemd unit, API and Wi-Fi route, updater state, maintenance action, plugin,
experience event, MCU message and recovery tool. `acceptance/coverage.json`
assigns every inventory item to an owner, executable suites, fault classes,
fidelity levels and any irreducible physical gate. CI rejects stale or unowned
inventory and missing profiles.

For every production path, test the success path, rejection path, restart
path, interruption boundary, retry limit, rollback or fail-closed behavior,
and evidence/privacy behavior where applicable. A source-only assertion is not
sufficient for an installed permission, identity, mount, firewall, service
ordering or packaging contract.

## Automated layers

1. **Static and contract tests** validate generated metadata, image contents,
   unit sandboxing, filesystem modes, configuration, schemas, parsers, release
   signatures, inventory ownership and evidence validators.
2. **Host unit and process tests** execute daemon, SIP, audio, web, story,
   Wi-Fi, OTA and recovery logic with deterministic clocks and fault injection.
   GCC, Clang, ASan and UBSan cover independent compiler and memory-safety
   failure modes; formal parser and state-machine checks remain CI gates.
3. **Peripheral co-simulation** preserves Alpha-to-I2C-to-Beta-to-USB routing
   and injects corrupt, duplicated, delayed, missing and reset traffic instead
   of directly mutating daemon state.
4. **Outside-in ARM64 QEMU** runs on `anima`. It exercises real systemd users,
   services and sockets; independent captive-portal and update clients; TLS
   origins; maintenance SSH; resource exhaustion; network loss; abrupt power
   cuts; every update journal boundary; quarantine; rollback and recovery.
5. **Exact-image QEMU** boots a disposable overlay of the factory-seeded image.
   It validates the assembled partitions, persistent mounts, read-only system
   assumptions, service accounts, runtime directory traversal, firewall,
   NetworkManager policy and early boot graph. The generic guest is useful for
   breadth but cannot satisfy this gate.
6. **Evidence coherence** binds local and QEMU results to one full source
   commit, requires every named scenario, requires an exact-image pass, and
   rejects any automated evidence that claims physical fidelity.

## Required automated release procedure

Run local coverage from a clean checkout and retain its JSON result:

```sh
python3 tools/generate_coverage_inventory.py --check
python3 tools/coverage_ledger.py validate
python3 tools/coverage_ledger.py run-automated --suite host --suite contracts \
  --evidence /path/to/local-evidence.json
```

Build and factory-seed the candidate on `anima`, then run the entire QEMU lab
with all three `MILLENNIUM_QEMU_EXACT_*` inputs set to that candidate image and
its transport kernel/initrd. Preserve both `full-test-result.json` and the
copied `exact-image-result.json` from the same artifact directory.

Finally produce the automated verdict:

```sh
python3 tools/release_gate.py \
  --local /path/to/local-evidence.json \
  --qemu /path/to/full-test-result.json \
  --exact /path/to/exact-image-result.json
```

Any missing, stale, generic-guest-only, incomplete or failed evidence rejects
the release. Fixes found by a gate require a new commit, new image, and complete
rerun; results from the predecessor cannot be carried forward.

## Physical-only residuals

Only physics and human-perception claims remain outside automation: Zero 2 W
firmware/tryboot selection, SD electrical behavior, real RF association and
native captive detectors, USB enumeration, MCU instruction timing, acoustic
quality, control voltages, brownouts, external-network provenance, and a
first-time owner's comprehension. Their exact procedures and GitHub issues are
generated by:

```sh
python3 tools/coverage_ledger.py physical-plan
```

These are run once, in the documented order, only after the automated release
verdict accepts the candidate. A physical failure rejects the image, becomes a
regression test at the highest feasible installed-image fidelity, and restarts
the automated procedure from a new commit.

## Regression rule

Every escaped defect must add a test that fails on the rejected artifact and
passes on the correction. The test must reproduce the boundary that failed.
For example, the captive portal permission defect is checked both by starting
the deployed Wi-Fi services and connecting to the broker as the real
`millennium-wifi` user, and by asserting the effective runtime-directory owner,
group and traversal permission while booting the exact production image.
